# 可行性、先行工作与风险

## 1. 结论先行

**可行，但是分阶段的工程/研究项目，不是“再写一个编译器”那么简单。**

已经成熟的部分：

- 依赖类型内核 + 证明擦除（Lean/Coq/Agda/Idris）；
- 精化类型 + SMT（Dafny/Verus/F*）；
- 验证 + C 级性能（F*/Low*/KaRaMeL/HACL*）；
- 无 GC 函数式运行时（Koka/Perceus、Roc、MLKit、Lean 4）；
- 线性/唯一性类型（Rust、ATS、Cogent）；
- 翻译验证/验证编译器（CompCert/CakeML/Alive2）。

尚未完全解决的部分：

- SMT 证明到小内核的通用重建；
- 精化 + 依赖 + 线性/区域 + 成本类型的统一；
- AI 生成 spec/证明的可靠性；
- 硬件无关语义 + 表示优化的端到端验证；
- 大规模 AI 重写的工程/安全/可重现。

## 2. 先行工作

| 系统 | 给我们什么 | 局限 |
|---|---|---|
| **Lean 4** | 小内核、`Prop`/`Type`、proof erasure、RC、编译器 | 不是“AI 优先”工具链；精化/成本类型弱 |
| **Coq/Rocq** | 最强内核/宇宙/inductive；大量形式化 | 提取/性能/自动化偏学术 |
| **Agda** | 依赖模式匹配、终止检查 | 工程/性能/自动化 |
| **Idris 2** | 数量类型（0/1/ω）、擦除、可执行 | 生态/性能 |
| **F\* + Low\* + KaRaMeL** | spec/impl 分离、提取 C、HACL* 级性能 | 工具链重；SMT 信任；学习成本 |
| **Dafny** | 自动验证、循环不变式、多后端 | 性能/运行时；SMT 信任；证明不可重建 |
| **Verus** | Rust 所有权 + SMT + ghost/tracked 擦除 | 信任 Z3；不是完整 AI 优化框架 |
| **ATS** | 依赖 + 线性 + 系统编程 | 学习/工程/可读性 |
| **Cogent** | 唯一性类型 + 生成 C + Isabelle 验证 | 领域窄；生态小 |
| **Koka** | Perceus RC、无 GC 函数式、性能 | 未验证 |
| **Roc** | morphic RC、无 GC | 未验证；生态早期 |
| **MLKit** | 区域推断、无 GC | 老；生态小 |
| **CompCert** | 验证编译器、语义保持 | 源语言固定；不解决源层验证 |
| **CakeML** | 验证编译器/运行时 | 同上 |
| **Alive2** | LLVM 翻译验证、SMT | 不是完整内核证明 |
| **Alethe/LFSC** | SMT 证明格式/检查 | 覆盖/集成仍在发展 |
| **LeanDojo/COPRA/AlphaProof** | LLM 证明生成 | 不稳定；必须内核检查 |

## 3. 我们的内核里程碑证明了什么

- 类 Lean 的 de Bruijn 内核可以在几千行 Rust 内实现；
- `Nat`/`List`/`Eq` + recursor + `Eq.subst` 足够写真实的归纳证明；
- `sum_ref` vs `sum_fast` 的等价证明可以通过；
- 错误证明会被拒绝；
- 证明项规模可控（当前 358 节点，不含展开的引理）。

这验证了“**小内核 + 可检查证明**”的可行性，不验证性能/擦除/优化。

## 4. 风险矩阵

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| spec 写弱/写错 | 高 | 高 | 差分/变异/反例/审阅；reference impl 作 oracle |
| SMT 证明重建 | 高 | 中 | 只用可出证书片段；其余标 `smt`；manual/tactic 兜底 |
| 依赖 + 精化 + 线性/区域统一 | 中高 | 高 | 分层：内核只管证明；精化/所有权独立检查；接口用 facts |
| 无 GC 性能 | 中 | 高 | 区域 + 唯一性 + RC 兜底；Koka/Roc/MLKit 经验 |
| 编译时间 | 高 | 中 | 增量/缓存/并行；证明无关性；只检查改动 |
| AI 证明可靠性 | 高 | 中 | 内核检查 + 反例 + 搜索/重试 |
| AI 优化正确性 | 中 | 高 | `refines` + 内核/翻译验证；不信任优化器 |
| 硬件表示优化 | 中高 | 中 | 先语义层；表示层后续；translation validation |
| TCB 过大 | 中 | 高 | 小内核；编译器产出可检查工件；验证后端 |
| 安全/供应链 | 中 | 高 | 能力类型/沙箱/provenance/审计 |
| benchmark 过拟合 | 高 | 中 | held-out/统计/多 workload |

## 5. 需要做的实验

1. **内核**（已完成）：两个 sum 实现 + 等价证明。
2. **擦除**：证明/索引擦除后运行时 IR 的大小/性能对比。
3. **多实现**：`spec`/`refines` + benchmark 选择。
4. **线性/唯一性**：`sum` 的原地版本，证明与 `sum_ref` 等价，测分配。
5. **SMT 证书**：线性算术 Farkas 证书 + 内核检查。
6. **表示精化**：`Array<Int>` → `PackedArray<I64>`，验证边界/溢出。
7. **AI 重写**：让 AI 生成 `sum_fast` 的变体 + 证明，统计通过率/时间。
8. **编译时间**：增量检查 1k/10k 行模块。

## 6. 主要判断

- **正确性路线可行**：小内核 + 证明擦除 + `refines` 是成熟的组合。
- **性能路线可行但有条件**：无 GC 函数式 + 唯一性 + 区域/RC 可以接近 C；不是所有代码都能“汇编级”。
- **AI 优化可行**：把 AI 当不可信重写器，spec + 内核当裁判；这是最现实的组合。
- **最大瓶颈不是内核，是 spec 质量与工程规模**：写得出证明不等于写对了 spec。
- **SMT 只能做提供者**：要“小内核 + 可重建证明”，就不能把 Z3 当验证者；用证书片段 + tactic 兜底。
- **硬件无关需要表示层**：语义/表示分离是正确方向，但布局/进制优化是后续大工程。
