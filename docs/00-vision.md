# 愿景与原则

## 一句话

**用可检查的证明，把“AI 生成/重写代码”从不可信变成可信；用类型与规格，让源码保持脚本式可读，让优化器去选择硬件表示。**

## 三个分离

### 1. 证明与验证分离

- **证明提供者**：SMT、证明搜索、LLM、人类。
- **验证者**：一个小的依赖类型内核。
- 提供者可以错、可以幻觉、可以被替换；内核只接受能检查的证明项。
- 这是 de Bruijn 准则：信任基尽可能小。

### 2. 规格与实现分离

- **spec**：类型、前置/后置条件、不变量、效果、成本、确定性。
- **reference impl**：可读、可执行、作为差分测试的 oracle。
- **optimized impl**：AI 生成或重写，可读性不保证，必须 `refines` 同一个 spec。
- 一个 spec 可以有多个实现；构建时按 profile/benchmark 选择。
- 小函数允许内联 spec；性能关键模块拆文件。

### 3. 语义与表示分离

- 源码使用**语义类型**：数学整数、序列、映射；不暴露字长、字节序、内存布局、进制。
- 优化器选择**表示**：`i64`、packed array、SoA、哈希表、二进制/十进制。
- 表示必须通过**表示精化**（refinement/translation validation）证明其行为符合语义。
- 只有显式观察表示的操作（序列化、`toString`、FFI、MMIO）才把表示写进 spec。

## 核心原则

1. **小内核**：`Prop`/`Type`、Pi、lambda、inductive、recursor、定义等价。证明项是普通项。
2. **证明可擦除**：`Prop` 证明、精化、生命周期/区域、类型索引、成本注解不进入运行时。
3. **类型可重化**：需要运行时的类型描述（`TypeRep`、布局、动态标签）是普通值，带不变量；默认不重化。
4. **纯函数式表面**：严格求值、ADT、模式匹配、结构递归；效果显式。
5. **唯一性/线性驱动原地更新**：纯表面，优化器在证明唯一性后 lowering 成可变 IR。
6. **无 RC/GC**：区域推断 + 唯一性 + 复制兜底；生命周期尽量由类型计算。
7. **规格优先**：先有 spec，再有 reference，再有 optimized；`refines` 机械检查。
8. **渐进验证**：`verified` / `checked` / `trusted` 三档；热路径要求 `verified`，边缘可 `checked`。
9. **AI 可用的编译器**：JSON goal、hole、反例、证明搜索、benchmark、provenance。
10. **可重现**：证明工件、benchmark 环境、AI 生成记录进入构建清单。

## 明确不做（当前阶段）

- 不追求人类学习成本最低；语法以无歧义、可审阅、易 diff 为主。
- 不做完整的通用程序语言前端；先内核、再表面、再优化。
- 不做 RC/GC；也不承诺所有代码都达到汇编级性能。
- 不把 SMT/LLM 放进信任基；它们只产生候选。
- 不在第一版做并发、浮点、FFI、完整 unsafe 语义；这些需要单独的逻辑层。
- 不在第一版做完整的硬件表示优化；先把语义层和 `refines` 跑通。

## 成功标准

- **正确性**：所有 `verified` 函数有内核检查的证明；错误证明无法通过。
- **性能**：适合的代码落在 C/Rust 的 1.5–2 倍以内；热路径无运行时边界检查。
- **可读性**：reference impl 人类可审；optimized impl 有 provenance 和 source map。
- **可维护性**：spec 改动后，受影响的 impl 被机械地重新验证；不靠人工同步。
- **AI 友好**：AI 可以通过结构化 goal/hole 迭代，不需要解析人类报错。
